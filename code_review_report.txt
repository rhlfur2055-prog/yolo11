  1. 전체 아키텍처 흐름도
================================================================================

1.1 시스템 개요
────────────────────────────────────────────────────────────────────────────────
  한국 차량 번호판을 자동 인식하는 시스템.
  YOLO 객체 탐지 + 다중 OCR 앙상블(PaddleOCR + EasyOCR + CRNN) 기반.
  정적 이미지 12/12 (100%) 정확도 달성.

1.2 전체 실행 흐름
────────────────────────────────────────────────────────────────────────────────

  [사용자 입력]
       │
       ├── GUI 실행: plate_gui.py → PlateGUIApp (Tkinter)
       │       │
       │       ├── VideoReader (Thread) → cv2.VideoCapture → 프레임 큐 분배
       │       │       ├── display_queue (maxsize=3) ──→ 화면 표시
       │       │       └── detection_queue (maxsize=2) ──→ OCR 처리
       │       │
       │       ├── DetectionWorker (Thread)
       │       │       ├── PlateEnginePro.process_frame() ← 핵심 파이프라인
       │       │       └── results_queue (maxsize=10) ──→ 결과 전달
       │       │
       │       └── Main Thread (tkinter mainloop)
       │               ├── _refresh_display() (33ms 주기)
       │               ├── validate_bbox() 필터링
       │               ├── PlateTracker.update() Ghost Detection
       │               └── _draw_overlay() 화면 렌더링
       │
       ├── CLI 실행: plate_engine_pro.py --input video.mp4
       │       └── PlateEnginePro.process_video() → 전체 프레임 순회
       │
       ├── 테스트: test_ocr_accuracy.py
       │       └── PlateEnginePro.process_frame() × 12장
       │
       └── 독립 실행: plate_recognition_4k.py --input video.mp4
               └── PlateRecognizer.process_video() → 상태머신 기반 처리

1.3 핵심 파이프라인 흐름 (process_frame 내부)
────────────────────────────────────────────────────────────────────────────────

  프레임 입력
       │
       ▼
  ① YOLO 탐지 (conf=0.25, max_det=3)
       │
       ▼
  ② Manual NMS + ROI 필터 + 크기/위치 필터
       │
       ▼
  ③ ROI 크롭 (35%H / 40%V 마진) + 500px 업스케일
       │
       ▼
  ④ Tracker 기반 OCR 스킵 판단
       │   (기존 트랙 3+ 감지 시 → 캐시 결과 재사용)
       │
       ▼
  ⑤ Tier 1 OCR: PaddleOCR × 3 전처리 (original, clahe, sharpen)
       │
       ├── Consensus 도달 시 → ⑧로 이동
       │
       ▼
  ⑥ Tier 2 OCR: PaddleOCR + EasyOCR × 3 전처리 (_inverted, bilateral, auto_contrast)
       │
       ├── 4+ 투표 도달 시 → ⑧로 이동
       │
       ▼
  ⑦ Extra Crops: 2줄 번호판 분리 크롭 + CRNN 보조
       │
       ▼
  ⑧ 위치 기반 분해 투표 (prefix + hangul + suffix 독립 투표)
       │
       ▼
  ⑨ HangulClassifier 초성 교차검증
       │
       ▼
  ⑩ PlateValidator 검증 + 지역명 보정
       │
       ▼
  ⑪ 신뢰도 조정 + 필터링
       │
       ▼
  ⑫ PlateTracker 추적 + DB 기록
       │
       ▼
  결과 반환

  순위   구간                        예상 시간     위치
  ────   ────────────────────────    ──────────    ──────────────────
  #1     Tier 1+2 OCR 앙상블         300~2000ms   L1756-L1934
         PaddleOCR 3~6회 + EasyOCR 0~3회
         전처리 이미지당 OCR 1회 × 최대 6개 메서드

  #2     YOLO 추론                   50~200ms     L1453
         해상도별 imgsz (640~1920)
         CPU 시 200ms+, GPU 시 30~50ms

  #3     HangulClassifier            50~150ms     L925-L1020
         PaddleOCR(det=False) × 6 변형
         초성 교차검증 (ㅅ/ㅈ, ㅁ/ㅂ)

  #4     Extra Crops 2줄 처리        50~300ms     L1936-L2000
         상/하 분리 크롭 PaddleOCR
         녹색 번호판: 최대 7개 추가 크롭

  #5     이미지 전처리 × 6           20~60ms      L1756-L1934
         CLAHE, sharpen, bilateral 등
         전처리 자체는 빠르나 6회 누적

  총합 예상: 프레임당 500~2500ms (CPU), 200~800ms (GPU)

5.2 동기/비동기 처리 여부
────────────────────────────────────────────────────────────────────────────────

  plate_engine_pro.py의 process_frame()은 완전히 동기(synchronous).
  내부에 async/await, threading, multiprocessing 없음.
  모든 OCR 호출이 순차적으로 실행됨.

  plate_gui.py에서만 3-thread 아키텍처로 비동기성 확보:
    - VideoReader → display_queue + detection_queue
    - DetectionWorker → process_frame → results_queue
    - Main Thread → display + overlay
  → 화면 표시는 비동기이나, OCR 자체는 단일 스레드 내 순차 처리.

5.3 OCR 호출 방식: 순차 vs 병렬
────────────────────────────────────────────────────────────────────────────────

  모든 OCR 호출은 순차(sequential):

    for method in ["original", "clahe", "sharpen"]:      # Tier 1
        preprocessed = ImagePreprocessor.<method>(roi)
        text, conf = self._run_ocr('paddle', ...)        # 순차 대기
        # validate + 후보 추가

    for method in ["_inverted", "bilateral", "auto_contrast"]:  # Tier 2
        text, conf = self._run_ocr('paddle', ...)        # 순차 대기
        if need_easyocr:
            text, conf = self._run_ocr('easyocr', ...)   # 순차 대기

  → PaddleOCR과 EasyOCR를 병렬 호출하지 않음.
  → 전처리 메서드 간에도 병렬화 없음.
  → 이것이 실시간 성능의 가장 큰 병목.

5.4 YOLO inference GPU 사용 여부
────────────────────────────────────────────────────────────────────────────────

  YOLO 초기화 시 GPU/CPU 자동 선택 (ultralytics 기본 동작):
    - torch.cuda.is_available() → GPU 사용
    - CUDA 미설치 시 → CPU 폴백

  코드에서 명시적 device 지정 없음 (L1453):
    results = self.model(frame_for_detect, conf=0.25, max_det=3, verbose=False)
  → ultralytics가 자동으로 사용 가능한 GPU 선택.

  PaddleOCR도 GPU 자동 감지:
    PaddleOCR(use_angle_cls=True, lang='korean')
  → paddlepaddle-gpu 설치 시 GPU 사용.

  EasyOCR 명시적 GPU 설정:
    easyocr.Reader(['ko', 'en'], gpu=True)

5.5 프레임 스킵 로직
────────────────────────────────────────────────────────────────────────────────

  plate_engine_pro.py (process_frame 내부):
    - 명시적 프레임 스킵 로직 없음
    - 단, 트래커 기반 OCR 스킵 존재 (L1550-L1596):
      기존 트랙 3+ 감지 + 3+ 투표 + gap<=1 → OCR 완전 스킵, 캐시 재사용
      → 안정적 트랙에 대해서는 사실상 프레임 스킵 효과

  plate_gui.py:
    - DETECTION_SKIP = 1 (L52): 모든 프레임을 detection_queue에 전달 시도
    - 그러나 detection_queue maxsize=2: 큐가 가득 차면 프레임 자동 폐기 (L540)
    - 결과적으로 자연스러운 백프레셔 기반 프레임 스킵:
      OCR 처리 중 → 큐 가득 → 새 프레임 폐기 → OCR 완료 시 다음 프레임 처리

  plate_recognition_4k.py (process_video 내부):
    - 상태머신: SCANNING 모드에서 N프레임 간격 처리 (skip_frames 설정)

5.6 큐/버퍼 사용 현황
────────────────────────────────────────────────────────────────────────────────

  plate_gui.py의 3개 큐:
    큐                  maxsize   생산자          소비자          폐기 전략
    ─────────────────   ───────   ──────────      ──────────      ──────────────
    display_queue       3         VideoReader     Main Thread     오래된 것 폐기
    detection_queue     2         VideoReader     DetectionWorker 무시(put_nowait 실패)
    results_queue       10        DetectionWorker Main Thread     오래된 것 폐기

  plate_engine_pro.py:
    - 멀티프레임 버퍼: deque(maxlen=MULTIFRAME_SIZE=2) per bbox
    - recent_plates: dict (트래커 상태)
    - 별도 큐/버퍼 없음

5.7 개선 제안 (참고)
────────────────────────────────────────────────────────────────────────────────

  현재 병목 원인 요약:
    1. OCR 순차 호출 — PaddleOCR/EasyOCR 병렬화 가능
    2. 전처리 메서드 과다 — 최대 6개, 조기 종료로 일부 완화
    3. HangulClassifier — 6개 변형 × PaddleOCR, 필요 시에만 호출
    4. CPU 환경에서 YOLO 200ms+ — GPU 필수
    5. 프레임 스킵 미적용 — 전 프레임 OCR 시도 (queue 백프레셔만 의존)

  7.2.2 3-Thread 아키텍처

    [Thread 1: VideoReader]
      역할: cv2.VideoCapture로 영상 프레임 읽기
      생산: display_queue (항상), detection_queue (매 프레임)
      루프: 영상 FPS에 맞춰 sleep, EOF 시 처음으로 루프
      제어: playing_event로 재생/일시정지

    [Thread 2: DetectionWorker]
      역할: YOLO 탐지 + OCR 인식 (PlateEnginePro)
      소비: detection_queue
      생산: results_queue
      특이사항: Phase 1 (YOLO만) → Phase 2 (OCR 포함) 2단계 출력
        - detect_only() 먼저 실행 (~50ms) → Phase 1 결과 즉시 전달
        - process_frame() 전체 실행 → Phase 2 결과 전달

    [Thread 3: Main (Tkinter)]
      역할: 화면 갱신 + 사용자 입력 처리
      주기: 33ms (self.after, ~30 FPS)
      동작: results_queue 드레인 → validate_bbox → PlateTracker.update →
            display_queue 드레인 → 최신 프레임에 오버레이 → 화면 표시

  7.2.3 프론트엔드-백엔드 통신

    통신 방식: queue.Queue (스레드 간 통신)
    프로토콜: dict 형식 결과 객체

    결과 dict 구조:
      {
        "plate": "12가3456",          # 번호판 텍스트
        "confidence": 0.85,           # OCR 신뢰도
        "bbox": [x1, y1, x2, y2],    # 바운딩 박스
        "is_valid_plate": True/False, # Phase 2 확정 여부
        "ocr_confidence": 0.85,       # OCR 신뢰도 (동일)
        "confidence_level": "HIGH",   # HIGH/MEDIUM/LOW
        "plate_type": "신형",         # 번호판 유형
        "vehicle_type": "자가용",     # 차량 유형
        "frame_count": 5,             # 감지 프레임 수
        "plate_crop": np.ndarray,     # 크롭 이미지
        "process_ms": 450.2,          # 처리 시간(ms)
      }

    GUI 측 PlateTracker가 엔진 결과를 다시 추적하는 이중 추적 구조:
      엔진 PlateTracker (plate_engine_pro.py) → 투표/Ghost 방지
      GUI PlateTracker (plate_gui.py) → 2-Phase 확정 + bbox 스무딩 + NMS
